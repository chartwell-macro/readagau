# Contributing to readagau

Thank you for helping improve `readagau`. Contributions are welcome when they
make the package more reproducible, source-faithful, portable and clear for
users of versioned Australian agricultural data.

Please use the [chartwellmacro@gmail.com](mailto:chartwellmacro@gmail.com)
for a reproducible bug or a proposed change, and read the
[support guide](SUPPORT.md) for
the information that makes an issue actionable. Do not disclose a suspected
vulnerability in a public issue; follow the
[security policy](SECURITY.md).

## Scope and evidence

Before proposing a parser, catalogue or public-API change:

- identify the product, release ID, release date, asset role and source URL;
- record the source SHA-256, structural expectations and parser/cache version
  in development evidence; and
- describe the expected rows, tables, series, missing-value markers, rights
  status and failure condition.

Keep changes focused. Preserve existing defaults, public signatures, output
columns, classes, attributes, dates, cache identity and typed
`agau_*_error`/warning conditions unless the change is explicitly designed,
documented and tested as an API change. A source-layout change should fail
closed with a useful condition rather than silently returning a partial table.

### Fixture and source-data policy

Files committed under `inst/fixtures/` are package-owned reduced or derived
synthetic structures. They exercise parser and validation branches offline;
they are not copies of official reports or workbooks. Do not commit official
source bytes, third-party observations, report artwork, logos, the
Commonwealth Coat of Arms, credentials or restricted cache contents. Source
names and HTTPS URLs in catalogues are metadata for identity and routing, not
a licence to redistribute source material. See
[`inst/fixtures/README.md`](https://raw.githubusercontent.com/chartwell-macro/readagau/HEAD/inst/fixtures/README.md)
and `agau_attribution()` for the package/source-licence boundary.

Examples and tests should use a bundled synthetic fixture or a temporary local
file. Live discovery is opt-in and should not be required for ordinary tests:

```sh
READAGAU_LIVE_TESTS=true Rscript -e \
  'testthat::test_local(".", reporter = "summary")'
```

Do not commit downloaded files or credentials produced while running that
command.

## Development workflow

1. Create a focused branch from the current published base.
2. Make the smallest change that addresses the issue. Keep discovery,
   download/cache, parsing and normalisation concerns separate.
3. Update roxygen help, examples, vignettes, NEWS or repository guides when
   the user-facing contract changes. Regenerate `NAMESPACE` and `man/` from
   their source comments when appropriate.
4. Add deterministic offline tests first. Include a controlled failure test
   for unsupported formats, malformed schemas or unavailable assets where
   relevant.
5. Check the rendered documentation and run the validation commands below.
6. In the pull request, summarise the behavior contract, evidence, fixture
   provenance/rights, tests and any known limitations.

The package supports R 4.1 or later. The PDF and some ZIP parsing paths need
the Poppler `pdftotext` executable; note its version when a change touches
those paths. Do not assume it is available on every developer or CI machine.

## Required checks

From the repository root, run the checks relevant to the change. The ordinary
test suite is deliberately offline by default:

```sh
Rscript -e 'testthat::test_local(".", reporter = "summary")'
R CMD build .
R CMD check --no-manual readagau_0.1.0.tar.gz
R CMD check --as-cran readagau_0.1.0.tar.gz
Rscript -e 'pkgdown::check_pkgdown()'
git diff --check
```

Use the tarball name generated by `R CMD build` if the package version
changes. If a check cannot run in your environment, say why and include the
exact command and output in the pull request. Do not weaken a test or hide a
warning merely to obtain a green check.

For network or source-layout changes, also explain the offline behavior, cache
side effects, timeout/error behavior and how source hashes and release
identity are preserved. Never include official source files in an issue or
pull request just to demonstrate a parser result; identify them by URL, date,
asset role and hash instead.

## Review checklist

Reviewers should be able to reproduce the result from the repository and a
small synthetic fixture. A useful change has:

- a clear user-facing purpose and limitation;
- stable output names, types, classes and provenance;
- no writes outside temporary or managed cache directories;
- no credential or restricted-data exposure;
- coverage for normal, missing-marker and failure paths; and
- an accurate documentation and NEWS update where applicable.

Please keep discussions factual and respectful. This repository does not
promise a response time or compatibility for every unverified upstream
release.
